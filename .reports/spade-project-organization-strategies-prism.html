SPADE / Product strategy research

Don’t choose one map.

Issue #10 tests where project work should live. It does not test how a developer decides what needs attention, enters one objective, follows a cross-project initiative, or jumps to a known destination. The highest-value prototype is therefore a small stack of complementary organizers—not a third all-purpose canvas.

Recommendation: retain sidebar-versus-global as the territorial baseline, then add three orthogonal experiments now: an Attention Deck, a Work-item Portal, and a Command Jump. Gate Initiative Lens, Focus Sets, and Atlas navigation behind evidence.

01 / Executive brief

The territorial decision is real—but incomplete.

SPADE’s own plan frames the canvas as a mind map of ongoing work, separates project, work item, and execution workspace, and makes Issue #10’s two views projections over the same records.[2][3] That gives the prototype unusual freedom: new ways of entering and viewing work can be tested without creating new truth.

SOURCED FACTIssue #10 tests territory.

Dedicated project canvases versus one global grouped canvas answer “where does repository work live?” with the same four-project mock record set.[1]

INTERPRETATIONMost switching starts elsewhere.

A developer may begin from urgency, an objective, a known issue ID, or a temporary cross-repo task. Those are different navigation intents, not alternative geometries.

RECOMMENDATIONPrototype layers, not rival worlds.

Keep one canonical record set. Compare entry, focus, retrieval, and strategic lenses while project/work-item/workspace identity remains explicit.

The product bet: SPADE should behave less like a folder tree with a canvas attached and more like a control room with several legitimate doors into the same spatial evidence.
02 / Reframe

Five organizing questions, not one.

Unrelated products repeatedly separate canonical ownership from personal attention, strategic intent, direct retrieval, and temporary context. Linear groups projects around objectives; VS Code preserves multi-root workspaces; PagerDuty prioritizes actionable incidents; Airtable presents many views over one dataset.[7][8][17][12]

03 / Prototype runway

Six concepts. Three now, three gated.

Order is based on distinct learning value, fit to SPADE’s present domain model, and how little new authority each mock requires. It is not a production roadmap.

Attention Deck

A calm launch surface for active, blocked, review, and recent work—borrowed from incident triage, not from task boards.

Tests

Whether the natural starting point is “what needs me?” rather than “which repository?”

Work-item Portal

A temporary focus lens around one issue/objective, with provenance, workspaces, and breadcrumbs back to territory.

Tests

Whether the objective—not the project—is the best unit for resuming and reviewing agent work.

Command Jump

A keyboard route to a project, issue, workspace, node, or status query that lands on the exact spatial target.

Tests

Known-item retrieval versus visual browsing, plus orientation after arrival.

Initiative Lens

An intentional cross-project roll-up around a mission, without replacing project execution context.

Gate

Only when a real cross-repository coordination scenario is observed; otherwise it manufactures hierarchy.

Focus Set

A personal, temporary multi-project session modeled after IDE multi-root workspaces, with independent viewport restoration.

Gate

Only when users repeatedly assemble the same cross-project task context. Never call it a “workspace.”

Atlas + Waypoints

Named spatial destinations and overview navigation, borrowed from whiteboard frames and game-map points of interest.

Gate

Only if the global canvas remains valuable at realistic density but panning becomes the failure mode.

04 / Prototype cards

What to build—and what would falsify it.

Each concept is deliberately thin. A prototype should expose a decision, not quietly become a new subsystem.

Command Jump

Direct retrieval

TEST NOW
Interaction
Ctrl/Cmd+K searches project names, issue IDs/titles, workspace branches, node titles, and commands such as “show blocked.” Results disclose type, project, status, and context trail.
Task
Reach a known workspace, then locate an unknown blocked item.
Success
User reaches exact targets and can state where they landed.
Failure
Ranking or scope causes wrong jumps, or users rely on search only because visible navigation is broken.
Distinct from #10

Purpose across repositories

CONDITIONAL
Interaction
Two read-only, explicit collections such as “SPADE release readiness,” showing contributing projects/work items and jump-to-portal actions. Never infer membership from geometry.
Task

User sees contributors and blockers while retaining project identity.

Initiative and project feel synonymous, or the lens simply mirrors every project once.
Distinct from #10

Focus Set

Temporary personal context

CONDITIONAL
Interaction
A named personal set—“Release review”—contains chosen project canvases or portals. Members retain viewports; add/remove never changes ownership.
Task
Resume a review that spans SPADE and a tooling repository.
Success
User reduces switching and correctly identifies every item’s canonical project.
Failure
The set becomes a permanent pseudo-project or is confused with SPADE’s checkout/worktree Workspace.
Distinct from #10
Tests episodic multi-project context rather than organization-wide structure.

Atlas + Waypoints

Global spatial wayfinding

CONDITIONAL
Interaction
In the global condition only, show a minimap plus labeled project/work-item waypoints and click-to-focus. Labels/icons accompany color.
Task
Reach an off-screen review, then describe where it sits relative to project and work item.
Success
Less pan/zoom hunting with preserved global awareness.
Failure
The atlas becomes a more usable sidebar—evidence that the global canvas is not carrying navigation.
Distinct from #10
Tests whether wayfinding rescues a promising but dense global world.

06 / Experiment design

One dataset. Six tasks. No decorative metrics.

Reuse Issue #10’s records and preserve its hull-versus-parent-group comparison. The added prototypes are routes and projections, so observed differences are less likely to come from different content.

Shared scenario

Four projects remain simultaneously represented. At least two have parallel issues. Statuses include active, blocked, review, done, and quiet. Workspaces vary across implementation, review, fix, and exploration.

Add one cross-project story: SPADE release work depends on a tooling fix; one review is waiting; one quiet project contains a failed/blocked item. Records, edges, membership, labels, and viewports stay identical in every condition.

Task sequence

  1. Resume the most appropriate item after returning to work.
  2. Open a known issue and explain its current provenance.
  3. Find the exact review workspace for a known branch.
  4. Identify the blocker across two repositories.
  5. Switch to unrelated work, then return to the original spatial context.
  6. Explain what is active elsewhere without opening every project.

Observe, don’t grade

No benchmark thresholds are asserted before pilot data exists. Record these comparable observations per task:

Completion pathSequence of views/actions
BacktrackingWrong destination or scope
Time to next actionFrom prompt to justified choice
ReorientationCan the user say where they landed?
Cross-project awarenessWhat else can they accurately describe?
Confidence + reasonRating plus qualitative explanation

Recommended comparison order

  1. Run Issue #10 baselines first.
  2. Add Portal and Command Jump to both.
  3. Add Attention Deck as an alternate starting state.
  4. Prototype Initiative only for the cross-project task.
  5. Test Atlas only in the global condition.
  6. Test Focus Set only after recurring multi-project behavior appears.
07 / Guardrails

Learn broadly without bloating Issue #10.

The architecture says planned boundaries remain proposals until a prototype proves them.[4] Treat every added concept as a removable presentation layer.

01

Never duplicate truth

All conditions read the same Project, WorkItem, Workspace, CanvasNode, and CanvasEdge records. Geometry never silently changes membership.[2][6]

02

Keep decisions orthogonal

Issue #10 chooses territorial boundary and grouping treatment. Deck tests attention; Portal tests focus unit; Command tests retrieval; Initiative tests purpose.

03

Protect domain language

“Workspace” already means a concrete checkout/worktree. Use “Focus Set” or “Session” for temporary multi-project context.[3][6]

04

Make spatial state accessible

Pair color with labels/icons, preserve visible keyboard focus, avoid hover-only actions, and respect reduced motion.[5]

What this research does not prove
Documentation from Linear, VS Code, PagerDuty, Miro, FigJam, Slack, Airtable, Notion, JetBrains, Apple, and Atlassian proves that the referenced interaction mechanisms exist—not that SPADE users will prefer them. Only direct prototype sessions in SPADE’s agent-development scenario can answer that.
Material uncertainty
SPADE does not yet have live GitHub/Paseo project management. Mock status may overstate operational truth. Initiative health, permissions, dates, ownership, ranking, and adaptive recommendations would all be speculative production semantics and remain outside these prototypes.
Decision trigger after testing
If Deck + Portal outperform territorial browsing for resumption while users still use project canvases for sensemaking, adopt a layered model. If users ignore every derived view and navigate spatially with confidence, keep the product canvas-first and add only Command Jump as an accelerator. If Atlas behaves like a sidebar, prefer explicit project navigation over preserving a global world for its own sake.
08 / Method & sources

Evidence, interpretation, limitation.

Research combined SPADE’s canonical documentation and issue with current primary product documentation from deliberately unrelated organizing domains. Load-bearing SPADE, Linear, VS Code, FigJam, Airtable, Slack, Notion, Compass, IntelliJ, Miro, and PagerDuty claims were checked directly. Product analogies are interpretations, not evidence of user preference.
