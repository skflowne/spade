Architecture

How the current application fits together and where planned integrations belong.

This page is a visual map. The foundation describes what is implemented today and the rules it enforces; the plan contains detailed product decisions and proposals.

Implemented Planned boundary

Current application

SPADE is one Electron application with three parts: a sandboxed React renderer, a preload bridge, and a main process that owns every record and every outside connection. Agents started through Paseo reach back into SPADE through the spade CLI and a local control server.

Core data relationships

A project is a root directory plus one canvas. The canvas holds the nodes and the two kinds of edges between them, the project's workspace, the saved viewport, the activity log, and the resources of removed nodes, which reconciliation never adds back. Projects, the selection, and settings are stored in index.json; each canvas is its own file.

Selected project-management presentation

Projects, trees, and automatic placement are implemented. Group containers are the next brick (B6) and remain planned.

  • Each project owns one canvas, which is the authoritative spatial surface for its nodes and edges. No record spans two canvases.
  • The sidebar is a derived project list and canvas switcher with running-agent and attention counts. It owns no state beyond the selected project.
  • Structure is a forest of child edges; a branch is a derived view of one node and its descendants. One generic tree mechanic in src/shared/tree.ts serves every node type, including agents and sub-agents.
  • Agents read and change the graph through the same commands as the user, via the spade CLI taught by a skill, not MCP. When an agent names no target, a spawned node becomes its own child.
  • Automatic placement of new nodes is one pure shared function that never overlaps nodes and never moves existing nodes.
  • Node chrome and inactive node bodies keep canvas pan and zoom; a body captures wheel and pointer input only after the user activates it, until Escape, a click elsewhere, or the node is collapsed, hidden, archived, or removed.
  • Planned (B6): a shared Group container that owns child bounds, nesting, movement, navigation gutters, and Fit / Full height for groups within one canvas. Group membership will be explicit; overlapping a group never changes it. There is no Project container and groups never separate projects.

Implemented integration boundaries

The P3 prototype's generic boundaries were copied into src/ and generalized; its GitHub, issue, pull-request, and checkout parts remain deferred in the prototype.

  • Typed renderer requests cross a sandboxed preload into one serialized main-process owner of records, which publishes every applied change back to the renderer. The renderer receives no credentials, filesystem access, or Paseo client.
  • SPADE persists its own records and exact external references as provider + kind + opaque ID in its application data directory, never inside project directories. Paseo stays authoritative for agents, workspaces, parent relations, and timelines.
  • One Paseo adapter on @getpaseo/client 0.17.0 owns one daemon connection, with readiness, reconnect, and client-owned observations. The confined internal DaemonClient import stays inside src/main/paseo.
  • Managed sub-agents relate to their parent through Paseo's durable parent identity, never through titles, prompts, paths, or ordering. Provider-native sub-agents are listed on demand and keep their last known list when Paseo can no longer read them.
  • Agents reach SPADE through a local HTTP control server on 127.0.0.1, found through a discovery file and called by launchers for POSIX shells, PowerShell, and cmd.exe, all in SPADE's data directory. A change without an agent identity is refused unless a person at a terminal passes --as-user.

Open risks: provider-native sub-agents cannot be read once their parent is archived; daemon-restart reconciliation is covered by fake-driver tests, not by a live run; long agent runs on Paseo 0.17 are untested. See plan §13.

Entity and integration boundary

Canvas behavior stays generic. Each node type has three parts that never import each other: a shared definition, an optional main-process adapter, and a renderer. External systems are reached only through main-process services.

Architecture rules

  • The generic canvas owns node position, size, selection, connections, lifecycle, and viewport navigation. Groups will add containment and nesting.
  • Node chrome and non-interactive surfaces never trap canvas zoom-in/out; interactive content captures input only while active. Groups will preserve navigation gutters between children.
  • Group will own reusable containment geometry as a visual hull; a project is a root directory with its own canvas, not a container.
  • The sidebar reads shared records and agent runtimes to switch canvases; it does not own a parallel navigation or persistence model.
  • An entity renderer owns only the content and actions specific to its node type. Tree behavior and placement never depend on the entity type.
  • Shared records and the command set in src/shared are the common contract across the renderer, the main process, and the CLI.
  • Every canvas change from the user, an agent, or reconciliation goes through the workspace gateway, with its actor.
  • Connections describe provenance and context; they are not an execution graph.
  • External systems are accessed only from the main process, through dedicated services; the renderer reaches them only through window.spadeHost.
  • Planned boundaries remain proposals until they are built.
