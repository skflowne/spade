Foundation

What SPADE does today and the rules the current code relies on.

Current state

SPADE is an early desktop prototype. Its Electron window compares dedicated per-project React Flow canvases selected from an expandable sidebar with a global canvas containing four colored project groups. A second control switches work-item presentation between non-parent visual hulls and React Flow parent groups.

Both strategies project the same deterministic in-memory records: four projects, ten work items, fifteen workspaces and twenty-eight canvas nodes. The scenario includes parallel issues, mixed workflow stages and one complete issue-to-PR workflow. Dedicated canvases remember each project's pan and zoom while the app is running.

There is no persistence, project loading, agent connection, GitHub connection, or real workspace management yet. Mock resource references preserve provider provenance without contacting those providers. The plan describes the intended product and records the prototype's selected direction; this page describes only what exists now.

Core concepts

The shared data model defines the main things SPADE will place and track:

ConceptMeaning
ProjectA project and its SPADE canvas, optionally linked to a local folder or Git remote.
WorkItemA piece of work, such as a GitHub issue, task, or investigation.
WorkspaceA specific checkout or worktree where work happens.
CanvasNodeAn item shown on the canvas. It belongs to a project and can be associated with a work item and workspace.
CanvasEdgeA relationship between two nodes, such as “spawned,” “delegated,” “references,” or “derived.”

Rules already enforced

  • All five records use the same data-format version so future changes can be identified.
  • Every node belongs to a project. Work-item and workspace associations are stored explicitly rather than guessed from names, branches, or connections.
  • A workspace ID identifies the workspace. Its path and branch are descriptive details and may change.
  • Edges describe how nodes relate; they do not execute or schedule work.
  • A node created from another node inherits its project, work item, and workspace.
  • The Electron and renderer code use the same record definitions from src/shared/domain.ts.

Code structure

AreaResponsibility
src/mainStarts Electron and opens a sandboxed window. It does not run canvas workflows.
src/rendererOwns deterministic prototype fixtures, derives every navigation/grouping projection, renders the canvas, and keeps node and per-project viewport state in memory.
src/sharedDefines the records, node types, and basic commands used to create and connect nodes.

The project comparison uses one generic prototype-record node presentation backed by deterministic fixtures. Existing generic canvas commands and the mock entity adapter remain available in the shared core; the prototype does not call an external service or create another record model. See the architecture diagrams for how these areas connect.

Developer commands

  • npm install — install dependencies from the lockfile.
  • npm run dev — start the desktop app for development.
  • npm run build — build the Electron and renderer code.
  • npm run docs:compare — serve the documentation with side-by-side comparison against the base branch. Use -- --base <ref> --page docs/<page>.html to override the defaults.
  • npm run typecheck — check TypeScript types.
  • npm run lint — check source and configuration files.
  • npm test — build the app and run its automated checks.
