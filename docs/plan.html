SPADE DOCUMENTATION

SPADE Plan

Product direction, the generic first usable version, recorded decisions, and open decisions.

Last updated: 2026-11-21

1. Product vision

SPADE (Spatial Agent Development Environment) is a desktop, graph/canvas-based development environment built around a spatial representation of agent work.

The canvas is a mind map of ongoing work, not an executable dataflow engine. Nodes represent live resources and durable artifacts: agent conversations, images, web pages, and later terminals, files, and boards. Directed parent-child connections record where each piece of work came from.

SPADE is deliberately workflow-agnostic. It does not assume GitHub issues, pull requests, reviews, or any particular agent workflow. The first usable version is built from a small set of generic bricks that adapt to any kind of work, for example agent and sub-agent runs, image review, and several fixed checkouts kept under one framework project folder:

Project            a root directory plus its own canvas (the sidebar switches canvases)
  Group            optional spatial hull around related nodes on the canvas
  Agent            Paseo agent, always started in the project's root directory
    Sub-agents     children of the agent
  Image, Web page  viewer nodes
  Rich conversation  paths, images and links become actions:
                     reveal in Explorer, or spawn as a new node in a tree

Everything on the canvas that has a lineage is part of a tree. Any node, including agents and sub-agents, can have children, and any artifact inside a node can start a new tree or join an existing one (§4.6).

Recorded decisions

These decisions were taken on 2026-11-21 and govern the first usable version. Prototypes P1–P3 answered their questions; the next work is production code, not further prototypes.

  • Generic over workflow-specific. The GitHub issue → agent → worktree → diff → PR workflow is not what SPADE is used for now, so it is not part of the first usable phase. It is deferred, not dropped: its code stays in the merged prototypes for later (§19).
  • GitHub is deferred. Issue, pull-request, review, check, diff, commit, push, and merge surfaces are not relevant to the first usable phase and are postponed to a later phase (§14).
  • Windows only. v1 targets native Windows. WSL, macOS, and Linux are out of scope and must not shape the design.
  • SPADE never touches user projects. The application keeps all of its own state in its application data directory (§4.7). It writes no files, markers, ignore entries, or Git state into project directories.
  • A project is a root directory plus a canvas. Each project has its own canvas, and the sidebar switches between canvases. There is one canvas per project, no global canvas, and no project containers; groups are never used to tell projects apart. Every agent starts in its project's root directory. This replaces an earlier decision for one global canvas and multi-folder projects.
  • Parent-child trees, not branches. The structural relationship is a parent-child edge. A "branch" is only a derived view: a child together with everything below it (§4.6).
  • Legible by default. Default sizes and automatic placement must leave enough room that every new node is readable without manual rearrangement (§8). Users will still move things; automatic layout never overrides them.
  • Prototypes stay as reference. The P3 work is merged to main and the prototypes remain in the repository. They are not extended and not imported; code is copied into src/ and generalized (§19).

2. Core design pillars

  1. Spatial work representation

    • Position and grouping communicate meaning.
    • Parent-child connections communicate lineage; reference connections communicate context.
    • Connections do not trigger execution.

  2. Everything useful can become a node, and every node can grow a tree

    • Live resources and static artifacts use the same outer node behavior.
    • Any node, and any artifact inside a node, can spawn a child node or start a new tree. The mechanic is implemented once, generically, not per entity.

  3. Projects, groups, and workspaces are separate concepts

    • A project is a root directory with its own canvas. The sidebar switches between project canvases.
    • Groups are optional, user-created spatial hulls inside one canvas, with no status or workflow meaning. They are never used to separate projects.
    • A workspace is the concrete working directory an agent runs in. It is a fact about a node, not a grouping unit.

  4. Paseo is the initial control plane

    • SPADE should use an unmodified Paseo daemon where possible.
    • SPADE owns the canvas, entity registry, renderers, and spatial persistence.
    • Paseo remains the source of truth for agents, workspaces, and normalized conversation events.

  5. Rich rendering without rebuilding every tool

    • Agent answers render as structured Markdown, Mermaid, full custom HTML/JavaScript, code, tool calls, and file references.
    • Paths, images, and links inside a conversation are actionable (§7.1).
    • Full IDE support, when added, means opening the file in an external IDE.

  6. SPADE owns its state and leaves projects alone

    • Canvas, layout, and entity references persist in SPADE's own application data.
    • Resource owners (Paseo, the filesystem) keep their own state; SPADE stores locators.

Explicit deferrals

  • No GitHub, pull-request, review, diff, commit, or push integration (§14).
  • No WSL, macOS, or Linux support, and no remote hosts.
  • No executable workflow/dataflow engine.
  • No worktree management. Users work in fixed checkouts; Paseo-managed worktrees can be added later.
  • No terminal, Monaco editor, LSP, whiteboard, or task-board entities until the bricks in §20 are in use.
  • No embedded full IDE; no containerized execution isolation.
  • No ACP or SPADE-owned MCP integration. Agents read and control the graph through a CLI tool plus a skill (§4.6).
  • No security hardening or sandbox restrictions for agent-authored HTML/JavaScript; runtime isolation may still be used to prevent CSS/lifecycle collisions.
  • No assumption that a branch name is workspace identity, and no use of Git branches as a canvas concept.

4. Domain model

4.1 Canvas node

A canvas node is a durable SPADE record pointing at content or a live resource owned elsewhere.

type CanvasNode = {
  version: DomainRecordVersion;
  id: string;
  entityType: string;
  entityVersion: number;
  title: string;
  shortDescription?: string;

  position: { x: number; y: number };
  size?: { width: number; height: number };
  collapsed: boolean;
  projectId: string;
  groupId: string | null;       // ordinary Group membership, explicit
  workspaceId: string | null;   // working directory, when the node has one

  config: unknown;              // versioned and validated by the entity definition
  resourceRef: ResourceRef | null;
  cachedPresentation?: {
    revision?: string;
    summary?: string;
    updatedAt: string;
  };

  createdAt: string;
  updatedAt: string;
};

A node does not copy a file, image, agent transcript, or browser page into the canvas record as its source of truth. It stores a locator and may retain a bounded presentation cache. Tree position is not stored on the node; it is carried by child edges (§4.6).

4.2 Resource reference

type ResourceRef = {
  provider: "paseo" | "filesystem" | "electron" | "spade" | string;
  kind: string;
  id: string;
  revision?: string;
};

Examples:

  • Paseo agent ID
  • Paseo provider-native sub-agent: parent agent ID plus sub-agent ID

Decided in SPADE-36: only nodes that point at a resource owned elsewhere carry a reference, and today those are agent nodes. Image and web page nodes have resourceRef: null; their config is the single source of truth for the path, SPADE asset ID (§4.7), or URL, so no second locator can drift from it.

4.3 Project

A project is a root directory and the canvas that belongs to it. It does not require a Git repository, and SPADE never inspects or changes the directory's contents beyond reading what the user opens.

type Project = {
  version: DomainRecordVersion;
  id: string;
  name: string;
  rootPath: string;      // absolute Windows path, as the user selected it
  createdAt: string;
};

The motivating shape is a framework project containing several fixed checkouts that the framework's own version control ignores. SPADE does not model the checkouts: the project's root is the framework directory, every agent starts there, and the agent works in whichever checkout the task needs. SPADE does not infer folder structure and does not care what any ignore file says.

Project creation and navigation

Every project owns exactly one persisted canvas, stored separately in SPADE's application data (§4.7). Nodes, groups, edges, and the viewport belong to one canvas, and no node, edge, or group spans two canvases in v1.

  • Open project… opens a native Windows folder picker, proposes the folder name as the project name, creates the project and its empty canvas, and switches to it. It is available as an overlay when no project exists and at the top of the sidebar.
  • The sidebar lists projects and switches the visible canvas when one is selected. It shows each project's name and running-agent activity, and restores each canvas's last viewport. It is a switcher, not a jump surface within a single canvas.
  • Removing a project removes only the SPADE project record and its canvas, never the directory.
  • Changing a project's root path is an explicit action; project identity is the SPADE ID, not the path.

4.4 Workspace

A workspace is the concrete working directory an agent runs in.

type Workspace = {
  version: DomainRecordVersion;
  id: string;
  projectId: string;
  cwd: string;                  // the project root in v1
  paseoWorkspaceId?: string;    // opaque Paseo identity
  name: string;
  createdAt: string;
};

Rules:

  • Workspace identity is the opaque SPADE/Paseo ID. A path or Git branch is descriptive and may change; it never identifies a workspace.
  • Membership is explicit through node.workspaceId; it is never inferred from an edge, a path, or a name.
  • Every agent starts in its project's root directory. SPADE does not create worktrees or choose a different starting directory.

4.5 Group

A Group is a user-created spatial hull with a title and color. It carries no status, source, or workflow meaning.

type Group = {
  version: DomainRecordVersion;
  id: string;
  title: string;
  color?: string;
  parentGroupId: string | null;   // groups can nest inside groups on one canvas
  position: { x: number; y: number };   // size is computed from members
  collapsed: boolean;
  createdAt: string;
};

Membership is explicit: dropping a node or group onto a group, or choosing Add to group, sets groupId/parentGroupId; dragging it out or choosing Remove from group clears it. Merely overlapping a group never changes membership, and moving a group moves its members. Groups live inside one project canvas.

4.6 Connections and trees

type CanvasEdge = {
  version: DomainRecordVersion;
  id: string;
  fromNodeId: string;               // parent for "child"
  toNodeId: string;                 // child for "child"
  relation: "child" | "references";
  origin?: "spawned" | "delegated" | "artifact";   // for "child"
  sourceArtifact?: { kind: string; value: string };  // for origin "artifact"
  label?: string;
  createdAt: string;
};

The tree mechanic

One generic mechanic applies to every node type. Entity code never implements tree behavior.

  • child edges form a forest: a node has at most one parent, cycles are rejected, and a node with no parent is a root. A tree is a root and all of its descendants.
  • A branch is not a stored thing. It is the derived view of one child and everything below it, and it is what users collapse, move, or archive as a unit. It has no relation to a Git branch.
  • origin records how the child came to exist: spawned by the user from a node, delegated by an agent to a sub-agent, or created from an artifact inside a node (an image, a path, a link). Origin is descriptive and does not change tree behavior.
  • references edges are optional, non-tree context links (§9). They never affect tree structure.

Every spawn-as-new-node gesture, whether from node chrome or from an artifact inside a node, asks for a target:

  1. Child of the source node (default).
  2. Pick a tree or node: attach as a child of any chosen node. Choosing a tree attaches to its root.
  3. Start a new tree: create the node with no parent.

Agent control of the graph

Agents are first-class operators of the canvas, not just content on it. An agent can read the structure and change the graph however the work requires, using the same generic commands as the user. The channel is a SPADE CLI tool taught by a skill, not MCP.

  • Read: list projects, groups, nodes, edges, trees, and branches; read a node's type, title, state, workspace, parent, children, and bounded context projection (§9). Reads are bounded and paged; the CLI never dumps full transcripts or pages.
  • Change: every canvas command in §5.3 and §4.6 is available: create and spawn nodes of any registered type, start trees, reparent, move, resize, collapse and expand, archive and remove, create and edit groups, connect references, and prompt or spawn other agents.
  • Default for spawning a child is tree continuation. An agent that spawns a child normally continues its own tree, either by itself (a new child of its own node, starting a new branch off the agent) or from a node below it (a child of a descendant in its own tree, continuing an existing branch). When the agent names no target, the child is a child of the agent itself. This is the default and the documented convention in the skill, not a restriction: the agent may name any other target, including a new tree, when the work calls for it.
  • Same invariants as the user. Agent commands pass through the same validation: tree rules (single parent, no cycles), the layout rules in §8, and project safety in §4.7. A graph command only ever touches SPADE records, never user files, so even a broad command cannot delete or rewrite project content. Agent-created nodes do not take over the viewport.
  • Attribution. The CLI identifies the calling agent from its own environment. Every agent-made change records the acting agent, so the UI can show who changed what and the user can undo or review it. An agent cannot act as another node.
  • Failure. A command naming a node that no longer exists fails with an error returned to the agent; it never falls back silently.

Scoping what an agent may touch (for example limiting it to its own subtree) is not part of the first usable phase. It can be added later as a permission setting without changing the command surface.

Agent CLI, transport, and skill delivery

Decided in B3:

  • Surface. One spade command. Reads: whoami, projects, tree, nodes, node, edges, activity, entities, providers. Changes: spawn (a child of the caller by default; --parent, --tree, or --new-tree otherwise), reparent, move, resize, rename, describe, edit, collapse, expand, archive, restore, remove (each with --branch where it applies), connect, disconnect, and prompt. Plus help and skill. Every command accepts --json; reads are paged. There is no viewport or focus command.
  • Transport. The running application serves a local HTTP control server on 127.0.0.1 with an OS-assigned port and a bearer token created at each start. It writes a discovery file, control.json, and three launcher shims into its own application data directory: bin/spade (POSIX sh, also for Git Bash on Windows, with forward-slash paths), bin/spade.ps1 (PowerShell), and bin/spade.cmd (cmd.exe, which re-parses quotes and special characters, so text goes through stdin). The shims run the bundled CLI with the application's own executable in Node mode, so agents need no separate Node install. The CLI identifies the calling agent from PASEO_AGENT_ID.
  • Skill delivery. SPADE appends a few lines to every agent's initial prompt naming the agent's node, its project, and the shim path; on Windows it lists the three launchers in that order. The agent runs spade skill to read the spade-canvas skill bundled with the CLI. Nothing is written into project directories or provider configuration.
  • An agent spawned through the CLI becomes a Paseo child of the calling agent.

Decided in SPADE-36:

  • No silent identity. A change or prompt without PASEO_AGENT_ID is refused with identity-required unless a person at a terminal passes --as-user to act as the user. Nothing falls back to the user silently. A spoofed PASEO_AGENT_ID is still not detected (§21).
  • Text through stdin. Any one free-text argument of a command can be - to read that value from stdin, the safe way to pass arbitrary text.
  • Stable error codes. Reducer, agent-service (agent-missing, paseo-unavailable, …), and control errors reach the CLI with their own code; only unexpected failures are internal.
  • Prompt attribution. A prompt one agent sends another starts with a line naming the sending node, so both the receiving agent and the user see who sent it. Prompts are not canvas commands and are not recorded in the activity log.

Commands: spawnChild(sourceNodeId, type, config, target, origin), startTree(type, config, placement), reparent(nodeId, newParentId | null) (moves the whole branch; rejects cycles; null makes the node a new root), collapseBranch / expandBranch (hides descendants and shows a count), and archiveBranch.

Removing a single node never deletes its children: they are promoted to the removed node's parent, or become roots if it had none. Deleting a whole branch is an explicit action. Removing a node removes only SPADE records.

A removed node stays removed. The canvas remembers the resource of every removed node (the newest 500), and SPADE's own reconciliation never adds a node for one of them again, also after a restart. A user or an agent creating that resource again clears its entry.

Sub-agents use the same mechanic. A managed sub-agent identified by Paseo's durable parent identity appears as a collapsed child node with origin delegated. A sub-agent can itself have children of any type, so a branch can start at a sub-agent and continue with images and web pages.

Edges are provenance and context. They do not schedule, trigger, or stream live data.

4.7 Persistence and project safety

  • SPADE persists to its own application data directory (Electron app.getPath("userData"); on Windows, under %APPDATA%). It never persists into a project directory. Each project's canvas is stored as its own record set so canvases load and save independently.
  • A single main-process owner serializes all writes. Records are versioned, writes are atomic (write to a temporary file, then rename), and a migration keeps a backup of the previous data.
  • SPADE never creates files, directories, marker files, ignore-file entries, or Git state inside a project directory. Its own operations on project directories are read-only. Reveal-in-Explorer and viewing images are reads. Files that agents create inside the directory belong to the agent's work, not to SPADE's state.
  • Deleting a project, group, or node removes only SPADE records and never deletes user files.
  • Images and artifacts are referenced by path. When SPADE must hold its own copy (for example a pasted image), it stores it in an asset store inside application data and references it by asset ID.
  • Paths are stored as selected and compared in a normalized, case-insensitive form. Windows drive letters, UNC paths, and long paths must be handled.
  • The renderer receives no direct filesystem access; it issues typed commands through a sandboxed preload (see the architecture page).

5. Entity architecture

5.1 Avoid a universal CRUD contract

The tentative spawn / read / write / partial_read / render contract is too generic:

  • Writing to a terminal, file, conversation, browser, diff, and whiteboard has unrelated semantics and risk.
  • partial_read is better represented as a projection, selection, range, or page on an inspect query.
  • Rendering is a SPADE UI responsibility, not a resource operation.
  • Resource creation may be synchronous, asynchronous, or may attach to an existing resource.

Use a small generic lifecycle plus typed entity capabilities.

5.2 Entity definition

type EntityDefinition<Config, Resource, Snapshot, Context> = {
  type: string;
  version: number;
  displayName: string;
  icon: string;

  configSchema: Schema<Config>;

  create(input: {
    config: Config;
    workspace: Workspace | null;
    sourceNode?: CanvasNode;
  }): Promise<{ resourceRef: ResourceRef | null }>;

  inspect(input: {
    node: CanvasNode;
    resource: Resource | null;
    projection: "summary" | "context" | "detail";
    cursor?: string;
    selection?: unknown;
  }): Promise<Snapshot>;

  actions: Record<string, EntityAction>;

  toAgentContext(input: {
    node: CanvasNode;
    snapshot: Snapshot;
    budget: ContextBudget;
  }): Promise<Context>;

  Renderer: React.ComponentType<EntityRendererProps>;

  dispose?(resource: Resource): Promise<void>;
};

5.3 Generic canvas commands

These operations apply to every entity:

  1. createNode(type, config, placement)
  2. spawnChild(sourceNodeId, type, config, target, origin) and startTree(type, config, placement) (§4.6)
  3. connectNodes(fromNodeId, toNodeId, "references")
  4. moveNode(nodeId, position)
  5. resizeNode(nodeId, size)
  6. reparent(nodeId, newParentId | null) and setNodeWorkspace(nodeId, workspaceId | null)
  7. collapseNode(nodeId) / expandNode(nodeId)
  8. archiveNode(nodeId) / removeNode(nodeId)
  9. focusNode(nodeId) / fitNodes(nodeIds)

Resource-specific operations remain typed actions exposed by the entity definition.

5.4 Examples of entity-specific actions

Entity Owner Example actions Context projection
Agent Paseo session prompt, interrupt, resume, archive, answer permission, spawn child status, objective, selected messages, latest result
Image Filesystem (or SPADE asset store) reveal in Explorer, reload, copy path, spawn child path, dimensions, optional caption
Web page Electron guest navigate, back/forward, reload, open externally, extract selected page data URL, title, explicit page extract
Terminal, later Paseo PTY create, send input, resize, capture, stop cwd, command, state, bounded output tail

5.5 Extensibility boundary

Entity types are registered through an entity registry. The first implementation may be compile-time registration; do not design a third-party plugin loader before the built-in entity contracts stabilize.

Each entity owns:

  • Config schema and schema migrations
  • Resource adapter
  • Supported actions
  • Inspect projections
  • Agent context projection
  • Body renderer
  • Resource lifecycle hooks

SPADE owns:

  • Node identity and persistence
  • Generic node chrome
  • Canvas position/size/collapse
  • Project, group, and workspace membership
  • Connections
  • Minimap representation
  • Common menus and navigation
  • Capability invocation and audit UI

6. Generic canvas containers

Canvas surfaces share one container contract rather than independently reimplementing movement, framing, and navigation controls.

Container hierarchy

  • Group container: the reusable auto-sizing spatial container for related nodes and nested groups on one canvas.
  • Node wrapper: the common outer container around an entity renderer.

Group containment communicates spatial organization. Membership remains explicit (§4.5); moving a container does not rewrite identities. Projects are not containers: each has its own canvas.

Container-owned behavior

  • Title, icon and short description
  • Group color and workspace label where relevant
  • Runtime status and reconnect/error state
  • Dedicated drag handle
  • Canvas zoom-in/out remains available when the pointer is over container chrome or any non-interactive container surface
  • Persistent navigation gutters between contained elements so dense layouts always leave space for outer-canvas pan and zoom
  • Automatic bounds for containers with children
  • Fit to center and fit the complete container in the viewport
  • Full height to center the container and scale it to the full viewport height, even when that makes its width overflow
  • Resize, collapse, focus and archive controls where supported
  • Spawn connected… menu
  • Connect existing… mode
  • Incoming/outgoing provenance controls
  • Open externally where supported
  • Minimap color, icon and label
  • Context-sharing indicator

Fit and Full height are present on Group containers and Node wrappers. They are common container navigation controls rather than entity-specific actions.

Renderer-owned behavior

The entity renderer owns only the node body and entity-specific toolbar/actions.

Interaction rule

Dragging starts only from node chrome. Editor selection, terminal input, browser interaction, scrolling, whiteboard gestures and links must not drag the node or pan the outer canvas. Canvas zoom-in/out remains available when the pointer is over Project, Group, or Node container surfaces, including node chrome. Containers with children preserve targetable gaps between those children; these navigation gutters route pan and zoom to the outer canvas even in dense layouts. A child renderer may consume wheel or pinch input only inside its interactive content; surrounding chrome, gutters, and non-interactive container space never become a canvas-navigation dead zone.

Heavy interactive renderers should support:

  • Inactive preview mode
  • Explicit activation/focus
  • Escape or chrome click to return control to the outer canvas
  • Lazy mount near readable zoom or when focused
  • Disposal/unmount without losing the durable resource

As built for node wrappers:

  • Collapsing, hiding, archiving, or removing the active node returns input to the outer canvas.
  • Escape that closes a dialog, popover, or menu does not deactivate the node behind it.
  • Fit, Full height, and every other focus move center within the canvas area left free by the breadcrumb bar and the minimap; Fit all frames the nodes in the area the minimap leaves free.
  • A node body that fails recovers when its record changes and offers Retry.

7. Required initial entities

The core (B1 to B3) needs one entity: the agent conversation. Image and web page viewers follow (B4), then the rich conversation actions that spawn them (B5). Everything else is deferred (§7.4).

7.1 Agent conversation

  • Uses Paseo normalized events rather than scraping terminal ANSI.
  • Renders Markdown, code, Mermaid, tool calls, file reads, edits, shell commands, permission prompts and results.
  • Tool calls and file reads use expandable panes.
  • Supports prompts, interrupt/resume, model/mode display and attention state.
  • Spawn: the caller selects provider, model, mode, and prompt. The working directory is always the project root. The mode default comes from a user setting; unattended runs depend on it.
  • Can spawn child nodes from any message, artifact, or the generic node chrome, using the tree mechanic (§4.6). When the agent itself spawns a child, it defaults to continuing its own tree, from itself or from a node below it; it can also read and change the wider graph through the agent CLI (§4.6).
  • Can attach selected connected nodes as bounded context (§9).
  • Each node's conversation UI state (draft, shared-context picks, pending annotations, loaded history, scroll position) survives collapse and level-of-detail changes for the renderer's lifetime.

Rich conversation artifacts

The conversation recognizes artifacts in agent and user messages and in tool output, and offers typed actions on each. Every action runs through a main-process command; the renderer never touches the filesystem or the shell.

Artifact Detected as Actions
File path Absolute Windows path, or path relative to the project root, optionally with :line Reveal in Explorer (selects the file), copy path; if it is an image, Open as Image node
Folder path Same detection, existing directory Open in Explorer, copy path
Image Image path, or image content produced by a tool or message Inline thumbnail with bounded height, enlarge, Spawn as Image node, Reveal in Explorer
URL http/https link Spawn as Web page node, open in the default browser, copy
  • Every Spawn as… action uses the target choice from §4.6: child of this conversation node (default), pick a tree or node, or start a new tree. The new node records origin artifact with the artifact locator.
  • Paths are checked for existence lazily, and missing or unknown ones again when the conversation changes or the path is clicked; missing paths render disabled rather than failing, and a check that fails shows the path as unknown, not missing.
  • Network paths. Decided in SPADE-36: a network (UNC) path outside the project root is never stat-ed, opened, watched, or served because it appears in conversation text. It shows as unchecked until the user explicitly asks for it (Check this path, Load, Reveal), which approves that path for the session. Paths inside the project root are always allowed. Mapped drive letters cannot be told apart from local drives and are not covered (§21).
  • Invariant: files are only revealed, never launched. Only showItemInFolder is used for files; openPath is used only for directories, so a path in a message can never execute a program.

Conversation expansion preferences

Conversation panels use configurable default expansion by event/content type, with global defaults and an optional per-conversation override.

type ConversationExpansionPreferences = {
  toolCall: boolean;
  diff: boolean;
  html: boolean;
  thinking: boolean;
  read: boolean;
};

const defaultConversationExpansion = {
  toolCall: true,
  diff: true,
  html: true,
  thinking: true,
  read: false,
};

The preference controls initial expansion only; users can always toggle individual panels without changing the default.

Subagents

  • Managed sub-agents appear as collapsed child nodes with origin delegated and are placed by the tree layout (§8).
  • Expanding a sub-agent follows or centers the node.
  • The agent/sub-agent structure is a view over normal nodes and edges, not a second graph model.
  • Provider-native sub-agents collapse into their parent agent node as a list. Each entry can open its conversation on demand as a delegated child; they are not placed on the canvas by default.

7.2 Image

  • Displays a local image file (PNG, JPEG, GIF, WebP, SVG) from its path, or from the SPADE asset store.
  • Default size follows the image's aspect ratio within the legibility bounds in §8; the user can resize.
  • Reloads when the file changes on disk. A missing or unreadable file shows an explicit state and keeps the node and its children. A network image outside the project root shows "not loaded" until the user clicks Load (§7.1).
  • Decided in B4: each image file SPADE has described is watched by polling that file's status, never its directory, so watching survives editors that replace files and files that disappear and return. At most 256 files are watched; the least recently described stop first.
  • Actions: reveal in Explorer, copy path, open full-size, spawn child (tree mechanic).
  • Large images are decoded lazily and downscaled for display; memory use is bounded by the performance strategy (§12).

7.3 Web page

Web page sources:

  1. Normal remote pages.
  2. Local application and dev-server pages.
  3. SPADE/agent-generated artifacts.

Remote pages and generated artifacts are different trust/rendering modes and must not share a privilege model.

Browser rendering architecture

  • A normal iframe cannot render many remote pages because of X-Frame-Options and CSP.
  • Electron WebContentsView is a native child view with window-relative bounds and cannot participate in React Flow transforms, clipping and stacking. Do not use one per node.
  • The P2 prototype selected the guest <webview>: it stayed live through pan, zoom, resize, clipping, stacking, reparenting, focus, keyboard, wheel, navigation, popup interception, remount and persistent sessions, including 20 simultaneous guests on native Windows. Electron still officially warns about <webview> stability; treat it as a monitored risk.
  • If guest stability later fails, fall back to one selected/expanded native overlay or a separate window, with its limitations stated.

Popups are denied and navigate the same guest. Guest sessions use a persistent partition. Long-duration and download behavior are untested and must be verified by the implementation. Until downloads are designed, the B4 implementation refuses them.

As built:

  • A guest takes calls as soon as it is attached, before dom-ready, which a page that never answers never fires.
  • An address set from outside the page, such as an agent changing the node's URL, wins over the page that was loading.
  • Page zoom follows the canvas zoom once it settles, not on every frame.
  • A crashed guest shows the failure, and Reload replaces it.
  • Below canvas zoom 0.5 the guest is unmounted and a placeholder shows the page's title and URL; above it the page returns at the same URL.

7.4 Deferred entities

Terminal, file editor (Monaco with LSP), diff/changes, whiteboard, task board, and GitHub issue/pull-request entities are not part of the first usable version. Their earlier designs remain in this page's Git history and in the merged prototypes. Add them through the entity registry when real use shows a need.

8. Default layout and placement

Layout is a first-class requirement. A user should be able to spawn agents, sub-agents, images, and pages and read everything without rearranging first. Users will move nodes; automatic layout only decides where new nodes start.

Rules

  1. Legible default sizes. Each entity declares a default size that is readable at 100% zoom. Initial values, to be tuned during the build: agent conversation 640×720; collapsed agent 320×96; web page 960×640; image scaled to its aspect ratio with its longest side 560 (minimum shortest side 240); containers size to their members.
  2. Reserved space. A placed node reserves its presented size plus spacing. Initial spacing: 96 between siblings and 160 between a parent and its children; trees are separated by at least 240.
  3. Collapsed nodes reserve their expanded footprint. Expanding a node or branch must never overlap a neighbor.
  4. Never overlap. No newly placed node may overlap any existing node, group hull, or container. When the natural slot is taken, the nearest free slot in the growth direction is used.
  5. Trees grow rightward. A child is placed to the right of its parent. Siblings stack vertically in creation order. Placement is subtree-aware: space is reserved for the extent of earlier siblings' subtrees so later siblings never land on them.
  6. New roots go in the first free slot below the existing content of the target container, left-aligned.
  7. User position is authoritative. Automatic layout never moves a node the user has placed or moved. A later explicit Tidy branch command may re-lay out one branch on request; it is not required for v1.
  8. Containers fit and keep gutters. Groups and projects auto-fit their members with padding and preserve the navigation gutters of §6.
  9. Viewport on spawn. After a user-initiated spawn, the canvas centers the new node at a readable zoom; it does not fit-all. Nodes created by agents (sub-agents) never take over the viewport.

Placement as built

B2 kept the initial sizes and spacing and settled the cases the rules above left open:

  • A first child is top-aligned with its parent. A later sibling starts below the lowest extent of the earlier siblings' subtrees, plus sibling spacing.
  • When the natural slot is taken, the new node slides down in the same column to the nearest free slot. It keeps sibling spacing from nodes of its own tree and tree spacing from other trees.
  • A new root goes 240 below the lowest existing content, left-aligned with the leftmost node.
  • Archived nodes reserve no space.
  • Centering a new node uses the canvas area left free by the breadcrumb bar and the minimap (§6).
  • Closing the spawn dialog while its node is being created does not cancel the creation; the node appears without taking the viewport or focus.

Implementation constraint

Placement is one pure, deterministic function over the existing rectangles, the parent, and the new node's size. It lives in shared code and is tested directly. Entity renderers never compute positions.

9. Context passed to agents

Connections do not automatically inject unlimited content. SPADE builds an explicit, bounded context projection.

type AgentContextReference = {
  node_type: string;
  node_id: string;
  node_name: string;
  short_description?: string;
  relation: "child" | "references";
  workspace?: {
    id: string;
    cwd: string;
  };
  locator?: {
    kind: string;
    value: string;
  };
  revision?: string;
  excerpt?: string;
};

Initial behavior:

  • On agent creation or prompt, SPADE includes selected connected node references and bounded excerpts in the prompt/attachment payload.
  • Full transcripts, complete web pages, entire whiteboards and large diffs are never silently included.
  • The UI shows which nodes are being shared.

There is no ACP or SPADE-owned MCP integration in v1. If on-demand node access later becomes necessary, it will be designed from observed context-projection limitations rather than prebuilt now.

10. ACP and MCP clarification

ACP

ACP is the Agent Client Protocol, a JSON-RPC protocol between an agent client/editor and a coding agent. It standardizes sessions, streaming, modes, permissions and related coding-agent interactions.

For SPADE v1, ACP is out of scope. Paseo may use it internally for compatible providers, while SPADE consumes Paseo's normalized agent model.

MCP

MCP is a tool/resource protocol between an agent host and external capability servers.

The harness/provider may support transporting MCP tools, and Paseo can inject MCP server configuration into supported providers. That does not automatically define how an agent reads SPADE nodes.

MCP is not used. Agent control of the graph (§4.6) is a CLI tool plus a skill. Prompt/attachment context projection supplies read context. Revisit a SPADE node tool service only after a prototype demonstrates that bounded prompt projections are inadequate.

11. Rich agent responses and generated HTML

V1 supports both standard rich blocks and full agent-authored HTML/JavaScript. Security hardening is explicitly deferred for the prototype.

Standard rich blocks

  • Markdown
  • Syntax-highlighted code
  • Mermaid
  • Tables, callouts and structured lists
  • Tool-call/read/edit/shell panes
  • Diff blocks
  • File, folder, image, and link references with the actions in §7.1

Custom HTML/JavaScript blocks

Agents may return complete custom HTML/JavaScript answer blocks. Render them in an unsandboxed iframe or separate document runtime so scripts execute and CSS/runtime lifecycle does not collide accidentally with the React application. The iframe boundary is for composition and resetability, not a v1 security boundary.

Direct innerHTML is insufficient because inserted script elements generally do not execute and unscoped CSS can damage the host UI. A document/iframe runtime also gives each answer a deterministic mount, reload, and disposal lifecycle.

Decided in B5:

  • Fence convention. A fenced Markdown block whose info string starts with spade-html renders as a live answer; any following words become its title. A plain html fence stays a highlighted code block that the user may choose to render. The spade-canvas skill teaches agents the convention.
  • Bootstrap runtime. Each answer is an unsandboxed iframe that loads a static bootstrap document shipped with the app. The bootstrap announces itself to the host, receives the answer through postMessage with a per-runtime token, and replaces itself with the answer document, which starts with the prelude that defines window.spade.
  • Resulting CSP. The app document keeps a strict Content-Security-Policy (script-src 'self'; img-src limited to the app, data:, and spade-image:; frame-src 'self'). The bootstrap is a separate document without a CSP of its own, so agent-authored scripts run there and the app's policy is not loosened for them.

Each artifact revision records:

  • Originating agent/turn
  • HTML, CSS, JavaScript and optional assets
  • Current user interaction/annotation state
  • Revision and creation timestamp

Not built yet: an HTML answer lives only in the agent's message in Paseo, and its annotations stay in memory until it is submitted (§21).

Interactive answer bridge

Inject a small SPADE API into each custom answer runtime:

window.spade = {
  submit(input: { message?: string; data?: unknown }): Promise<void>;
  annotate(input: {
    target?: string;
    text: string;
    data?: unknown;
  }): Promise<void>;
};

Initial use cases:

  • Rich plans with inline comments and annotations
  • Forms or choices whose values become the next user message
  • Editable structured recommendations
  • A Submit feedback action that sends the artifact revision, annotations, and entered data back to the originating agent

User submissions become explicit conversation events/follow-up prompts; custom scripts do not mutate the canonical conversation directly. As built, each answer has at most one submission in flight; its annotations leave with it and come back if the prompt fails. Escape inside an answer returns control to the canvas unless the answer handled it.

Accepted prototype risk

An unsandboxed, same-origin Electron document is more privileged than opening a generated HTML file in a normal external browser because it may share application origin, state, or exposed preload APIs. Security is not a v1 constraint, but the implementation should record this accepted risk and keep the custom runtime replaceable so isolation can be added later without changing the artifact contract.

12. Canvas navigation and scale

Large-canvas navigation is a core feature, not polish.

Required behavior

  • Fit the entire project canvas
  • Allow canvas zoom-in/out over every container's chrome and non-interactive surface
  • Preserve navigation gutters between contained elements for outer-canvas pan and zoom
  • Expose Fit and Full height controls on every Group container and Node wrapper
  • Switch to a project canvas immediately from the sidebar, restoring its last viewport
  • Center/focus a node
  • Follow an edge to its source/target
  • Back/forward focus history
  • Search nodes by title/type/status within a canvas
  • Keyboard navigation between related nodes
  • Breadcrumb or current-focus indicator
  • Minimap overview with group colors, nested groups, and node-type icons

Minimap and level of detail

React Flow's minimap is SVG-only and should show simplified node representations.

At overview zoom:

  • Hide heavy node bodies.
  • Show title, type, status, group color, and compact workspace label when relevant.
  • Keep group boundaries and meaningful edges visible.
  • Allow minimap click/drag to center quickly.

The exact zoom thresholds must be tuned during the build; do not hard-code product semantics around an arbitrary initial value. As built, node bodies switch to their preview below canvas zoom 0.5; a web page's preview is a placeholder with its title and URL (§7.3).

Performance strategy

  • Lazy-mount Monaco, tldraw, xterm and browser renderers.
  • Preserve external resources when a renderer unmounts.
  • Use cheap preview shells when zoomed out.
  • Avoid keeping every browser/editor/terminal active on a large canvas.
  • Test 100 mixed nodes and a smaller number of simultaneously active heavy nodes.
  • As built: canvas pushes are structurally shared in the renderer store, so nodes whose records did not change do not re-render, and a live page applies a new zoom only once the canvas zoom settles.

13. Paseo integration boundary

Paseo's current architecture is a good technical fit:

  • Node daemon with WebSocket protocol
  • Published @getpaseo/client
  • Agents, workspaces, providers and configuration in the public facade
  • Normalized timelines, permissions and tool events
  • Worktree, terminal, Git/forge, browser and filesystem operations in lower-level APIs
  • Multiple existing clients prove the daemon is not tied to one UI

Adapter rule

All Paseo access goes through one SpadePaseoAdapter.

SPADE entity adapters
  -> SpadePaseoAdapter
       -> public @getpaseo/client where available
       -> isolated low-level protocol/internal client usage where unavoidable
  -> unmodified Paseo daemon

Do not spread direct protocol calls through entity renderers.

Production adapter

The production adapter in src/main/paseo was built in B3 by copying and generalizing the P3 adapter, which was written against Paseo 0.14.0, and moving it to @getpaseo/client 0.17.0. Everything GitHub-, issue-, pull-request-, and checkout-specific stays for the later phase that revisits it. Behavior kept:

  • One daemon connection with explicit readiness and reconnect. A missing daemon is a normal state that recovers on its own.
  • Identify the client with a semver appVersion; a non-semver value hides non-legacy providers from the session.
  • Exact agent reads, spawn with caller-selected cwd/provider/model/mode/prompt and an optional durable parent, prompt, interrupt, archive. The agent service archives an agent only to roll back a spawn whose creation command failed after Paseo created the agent; removing or archiving a node never touches its agent.
  • Durable managed-child identity and parent relations, mapped to child edges.
  • Normalized, bounded timelines that tolerate changed epochs/ranges after a daemon restart.
  • Pending permissions presented on the agent node and answered through a generic command.
  • Persisting opaque agent and workspace identities before any fallible refresh, so restarts never duplicate nodes.

The daemon address comes from the SPADE setting, then SPADE_PASEO_URL, then the listen address the local daemon records in its paseo.pid or config.json, then Paseo's default ws://127.0.0.1:6767/ws. It is resolved once when SPADE starts, so a daemon started later on a non-default port is found only after SPADE restarts (§21).

What changed with Paseo 0.17

  • The client owns its subscriptions: SPADE opens agent and event observations that survive reconnects, instead of the prototype's polling. The daemon sends agent updates and session events only while an observation is open.
  • Agents spawned by other agents are background agents. Observations and child lookups pass filter.includeBackground to see them; this replaces the 0.14 background-workspace opt-in.
  • Timelines are read in the projected projection.
  • Provider-native sub-agents can no longer be read once their parent is archived. SPADE keeps the last known list and marks it unobservable.
  • User and assistant messages in 0.17 timelines carry no images; images reach the conversation only through tool output and image paths.

Known technical risk

The public Paseo SDK facade still cannot share one connection across agents, timelines, provider sub-agents, and event observations, so the adapter keeps one confined internal DaemonClient import. Complete sub-agent coverage after parent archival is impossible on 0.17. The full Claude run that stalled on 0.14 was not reproduced on the short runs of the live validation scripts; long runs remain untested. npm run test:live has passed against a real Paseo 0.17.0 daemon, including a relaunch of SPADE, but it never restarts the daemon: reconciliation after a daemon restart is covered by fake-driver tests only. SPADE keeps these dependencies isolated.

Plugin boundary

Paseo's plugin system may be useful for daemon-side SPADE RPCs later, but a complete React Flow shell does not fit naturally as a Paseo sidebar plugin. SPADE remains a separate frontend.

14. GitHub and Git scope

Deferred, not dropped. The first usable phase has no GitHub adapter, no gh dependency, no issue or pull-request entities, and no diff, commit, push, or merge surfaces. Agents may use Git freely inside their working directory; SPADE neither requires nor models it.

The earlier GitHub entities, adapter, reconciliation, and checkout operations remain in the merged P3 prototype. When this scope is picked up in a later phase, it comes back as ordinary entities registered through §5, not as a built-in workflow.

15. Full IDE and file explorer

Do not embed a full IDE. In v1, SPADE provides Reveal in Explorer for files and folders (§7.1) using the Windows file explorer. An Open in IDE action is deferred; when added it targets VS Code on Windows paths (code -g path:line:column) with configurable command templates for other editors.

16. Desktop shell and browser rendering

Why WebContentsView does not behave like a React Flow node

React Flow pans and zooms its renderer DOM with a CSS transform matrix. Electron WebContentsView is not a DOM child: it is a native/main-process child view attached to the application window and controlled through rectangular window-relative { x, y, width, height } bounds.

It can be synchronized approximately by recalculating screen bounds on every pan, zoom, resize, scroll, and node move, but it does not naturally inherit:

  • CSS scale/transforms or arbitrary clipping
  • Rounded node clipping and DOM masks
  • DOM stacking between edges, node chrome, menus, and overlapping nodes
  • React layout and unmount order
  • Pointer routing from DOM elements drawn above it

A collection of live native child views can therefore occlude canvas UI or drift during transforms unless SPADE builds a dedicated overlay compositor.

Does Tauri solve this?

No. Tauri 2 supports multiple webviews, but they are also window-attached native views with explicit logical x, y, width, and height, manipulated using setPosition and setSize. They do not become arbitrary transformed DOM descendants of React Flow nodes.

Tauri trade-offs:

  • Smaller application and Rust capability model
  • Uses platform webviews rather than one bundled engine
  • Cross-platform differences between WebView2, WKWebView, and WebKitGTK
  • Requires the same bounds-synchronization/compositor work for canvas browser nodes
  • Adds Rust/native integration work without directly improving Paseo's Node/TypeScript ecosystem fit

Electron trade-offs:

  • Larger package/runtime footprint
  • Bundled Chromium gives consistent rendering
  • Direct Node/native-module fit for Paseo, node-pty, Monaco, and the existing TypeScript stack
  • Provides the DOM-like <webview> guest element, implemented using an out-of-process iframe, which is much closer to React Flow composition
  • Electron officially warns that <webview> has stability risks in rendering, navigation, and event routing

Current recommendation

Electron remains the shell and the Web page node uses the guest <webview> selected by P2 (§7.3). Tauri solves none of the defining composition problems and is not planned. P2 passkey authentication succeeded on native Windows, which is the only supported platform.

21. Open decisions

  1. Final default sizes and spacing in §8. B2 kept the initial values; tune them against real content.
  2. Which connected nodes are included automatically as agent context versus requiring explicit selection (§9). Today only explicitly selected nodes are included.
  3. Acceptable active-node budget for webview and conversation renderers on a large canvas. Today at most 12 web page guests per canvas stay live.
  4. Long-duration <webview> stability and downloads (refused for now).
  5. Mapped network drives. A mapped drive letter cannot be told apart from a local drive, so the network-path rule (§7.1) does not cover it.
  6. Packaged-build behavior of the CLI launchers. They run the application executable with ELECTRON_RUN_AS_NODE, which a packaged build only honors with Electron's RunAsNode fuse enabled, and the CLI script must stay readable outside an asar archive. There is no packaged build yet, and none of the Windows launchers (spade under Git Bash, spade.ps1, spade.cmd) has been run on Windows.
  7. Per-agent credentials for the CLI. Today it trusts the caller's PASEO_AGENT_ID, so a spoofed identity is not detected (§4.6).
  8. Finding a Paseo daemon started after SPADE on a non-default port without restarting SPADE (§13).
  9. Undo for agent changes. Today they can only be reviewed, in the Activity panel and on recently changed nodes.
  10. Storing HTML answers as artifact revisions (§11).
  11. Live verification of reconciliation after a Paseo daemon restart, covered by fake-driver tests only (§13).
  12. Remote Paseo hosts and non-Windows platforms. Both are out of scope for v1.
